# ADR 0016 — Audio cues for room and operator

## Status
Proposed.

## Context
The system today is silent. A tracking session starts with a banner change; a snapshot saves with no acoustic confirmation; a question advances and only the operator's eyes know. From the gallery — three meters above the floor, ten meters from the laptop — *visual confirmation is unreliable*. The operator alt-tabs to make sure the click landed; the audience never hears the system acknowledge them.

The slide deck (`SLIDE 18 · FACILITATOR CUES`) treats silence as material — but silence isn't the same as no signal. It's the *absence* of unnecessary signal. A short bell that confirms "snapshot saved" is *less* disruptive than an operator visibly second-guessing the laptop, because it doesn't pull the room's attention back to a screen.

## Decision
Add a Web Audio layer to `/`, `/admin`, `/present`, `/project`. Every meaningful event triggers a short, generated tone:

| Event                                          | Cue                                  | Heard on        |
| ---------------------------------------------- | ------------------------------------ | --------------- |
| Snapshot recorded                              | Soft bell, ~250 ms                   | operator + room |
| Tracking starts                                | Low rumble fading over 2 s           | operator        |
| Tracking stops                                 | Reverse rumble                       | operator        |
| Cluster of ≥5 forms (first time in 10 s)       | Soft chord                           | room            |
| Question advances                              | Page-turn whoosh                     | operator + room |
| Drift warning (ADR 0015)                       | Quiet alarm tone, 1 s                | operator only   |
| Control card recognized (ADR 0014)             | Click confirmation                   | operator only   |

All sounds are generated by `OscillatorNode` + `GainNode` — no audio files, no licensing. Each is short (<2 s), low contrast (mid frequencies, soft envelopes), routed through a master volume on `/admin`.

A per-question `silent_mode` tag (default off, force-on for any `privilege_walk` question) suppresses *all* room-facing cues for the duration of that question — the privilege walk's silences are inviolable.

## Consequences

**Positive:**
- The operator stops alt-tabbing. They can act with confidence: every gesture has an acknowledgement they can hear.
- The room feels acknowledged. The system stops being invisible infrastructure.
- Snapshot timing is now *audible* — useful for retrospective video editing later.

**Negative:**
- Another failure mode (a bug muting all audio is silently degrading). Mitigation: a `?debug-cues=1` flag plays each cue once on page load.
- Browser autoplay policies require a first user gesture before audio starts. Mitigation: the existing "Start camera" button doubles as the audio-init action.

**Risks:**
- A bell during a vulnerable privilege-walk silence ruptures the room. Mitigation: `silent_mode` is force-on for that formation and surfaced visibly in `/admin`.
- Cue fatigue — too many sounds, the operator stops registering them. Mitigation: each cue is per-event, not periodic; the highest-frequency cue is "snapshot" and fires deliberately.

## Alternatives considered
- **Pre-recorded sound files** — heavier, harder to tune, licensing complications.
- **TTS confirmation ("Snapshot saved")** — too dominant; competes with whatever's being said in the room.
- **No audio** — current state; works but loses a high-bandwidth feedback channel for free.
